# Документация подсистемы: Синхронная виртуальная шина (VirtualBus & Рантайм)

## 🏛️ Архитектурные императивы
1. **Declarative by design**: Вся конфигурация, маршруты и связи задаются декларативно в виде путей (`MapPath`). Рантайм является чистым исполнителем воли метаданных.
2. **Performance first**: Zero-allocation концепты на горячих путях. Использование `ref struct MapPath` над `ReadOnlySpan<char>` для парсинга путей без выделения памяти в куче.
3. **Convention over configuration**: Изоляция контекстов и трансляция координат происходят автоматически на основе геометрии путей, без явных инструкций со стороны бизнес-логики.
4. **Hierarchy of State**: Дерево путей представляет собой иерархию состояний (в памяти шины). Бизнес-логика (Элементы) не хранит состояние в собственных полях, а использует память шины.

---

## 📐 Модель вычислений: "Physics of Prius"

Взаимодействие внутри системы жестко разделено на два изолированных конвейера: строго синхронный логический такт шины и фоновый I/O барьер (Data Intents).

1. **Unidirectional Flow (Однонаправленный поток)**: Сигналы текут строго сверху вниз через вызовы `Put`. Механизм `Notify` (баблинг событий вверх) упразднен. Реакция на изменения происходит либо через прямой спуск сигналов (`Put`), либо через фоновое выполнение намерений (`Intents`), которые возвращают результат в корень шины через `PutAbsolute`.
2. **Stateless Logic (Без состояния)**: Элементы (реакторы) атомарны и не имеют внутреннего состояния. Они работают с общей памятью шины через `ElementContext`. Контекст гарантирует доступ к памяти именно в той точке монтирования (mount point), где находится элемент.
3. **Implicit Memory Fallthrough ("No Wormholes")**: Если элемент делает `context.Put("sub/path", value)` и по этому пути не зарегистрирован другой элемент — данные автоматически, "по умолчанию", записываются в узел памяти шины (`_memoryRoot`) по этому относительному пути. Это позволяет элементам использовать вложенные пути как встроенное DTO-хранилище.
4. **Environment Merging**: Контекст предоставляет иерархическое окружение (`Env`) с четким приоритетом резолва: `Dynamic Patch (аргумент вызова)` > `Static Env (привязанный при монтировании маршрута)` > `Parent Env`.

## ⚙️ Механика маршрутизации и исполнения

Когда внешний или фоновый триггер инициирует `Put` или `Get`, запускается конвейер:

[Сигнал Put/Get] ──> [Узел блокировки] ──> [RoutingTrie.ResolveScoped] ──> [IElement.Put/Get] ──> [Memory Fallthrough]

### 1. Префиксное дерево (RoutingTrie) и Перехват сегментов
Поиск исполнителя (`IElement`) осуществляется через высокопроизводительное префиксное дерево (`RoutingTrie`). Дерево поддерживает:
* **Terminal Match (Точное совпадение)**: Если промежуточный узел пути имеет привязанный `TerminalElement`, маршрутизация немедленно останавливается, и управление передается этому элементу. Это позволяет элементам-родителям (например, `GateElement`) перехватывать все обращения к дочерним путям и действовать как фильтр или песочница без необходимости явных вайлдкардов.
* **Wildcard `*`**: Одиночный вайлдкард срабатывает только на последнем сегменте пути, если нет точного совпадения.
* **Deep Wildcard `**`**: Глубокий вайлдкард выступает как фоллбэк для всех путей глубже текущего узла, если ничего более точного не было найдено по ходу спуска.

### 2. Точка отсчета и Относительные координаты
Реакторы изолированы в своих координатных сетках.
* `RoutingTrie.ResolveScoped` находит нужный элемент, рассчитывает статическое окружение и отрезает уже пройденный префикс.
* Элементу через метод `Put` или `Get` передается только **оставшийся относительный путь** (`RemainingPath`) и специализированный `ElementContext`. Элемент считает себя корнем и работает только с путями относительно точки своей регистрации.

### 3. Иммутабельный лог контекстов (Стек вызовов)
На каждом шаге погружения (когда один элемент вызывает `context.Put`, перенаправляя запрос глубже) шина формирует вложенный `ElementContext`. Каждый контекст хранит:
* Ссылку на `Parent` (вышележащий контекст).
* Текущий `CallerSegment` (ключ узла, в котором мы находимся).
* `Node` — прямой доступ к узлу памяти `IMap`, соответствующему этой точке в общем дереве состояний.

### 4. Иерархическое окружение (Env)
Объект `ElementContext` сам по себе реализует интерфейс `IMap`, являясь агрегацией окружения. При обращении `context["key"]` он ищет ключ в следующем порядке:
1. `_envPatch` (динамический патч, переданный при текущем вызове `Put`).
2. `_staticEnv` (окружение, статически привязанное к маршруту в `RoutingTrie`).
3. Рекурсивный поиск в `Parent`.

Попытки записи в `context["key"] = value` молча игнорируются, так как Env предназначен только для чтения контекстных настроек спуска. Реальные данные должны писаться через `context.Put("path", value)`.

## 🔒 Многопоточность и Реентерабельность

Шина не использует семафоры с асинхронным ожиданием (`SemaphoreSlim`), так как архитектура подразумевает строго синхронный (импульсный) спуск.

* **Узловые блокировки (Node Locks)**: Для обеспечения потокобезопасности используются обычные реентерабельные блокировки `lock(object)`. Пул объектов блокировок разделен по абсолютным путям (в `_nodeLocks`).
* **Реентерабельность**: Благодаря использованию монитора (`lock`), один и тот же поток может рекурсивно вызывать `context.Put` или `context.Get` на том же узле, не вызывая Deadlock. Это необходимо для элементов, которые модифицируют свое собственное состояние перед тем, как пропустить сигнал дальше (например, распаковка данных).
* **Глобальный предел**: Для защиты от бесконечных циклов введена константа `MaxDispatchDepth` (по умолчанию 128). Если глубина вызовов превышает этот лимит, шина выбрасывает `InvalidOperationException`.

## 🚀 Асинхронные барьеры и PutAbsolute

Поскольку `Put` строго синхронен, длительные операции (например, запросы в сеть или БД) оформляются через механизм Intent'ов.

* Элемент записывает декларативное намерение в специальный путь, который перехватывается реестром намерений.
* Обработчик намерения (например, в фоновом потоке базы данных) выполняет I/O операцию.
* По завершении, фоновый поток использует `context.PutAbsolute(absolutePath, resultValue)`. Этот вызов не блокирует фоновый поток — он отправляет задачу в `ThreadPool`, где она инициирует совершенно новый, чистый нисходящий такт `Put` от самого корня шины. Это гарантирует сохранение "Physics of Prius" — все изменения происходят только движением сверху вниз.
